# the-world 团队协作机制 v1

> **版本**：v1.0（2026-09-17，`[协作]` 线 T-3/T-4 交付）
> **性质**：协作机制的**单一汇总文档**（single source）。条款的权威原文仍在 `AGENT.md` /
> `_share/README.md` / `_share/路线共识.md`；本文做索引、流程图与度量，**与原文冲突时以原文为准**。
> **边界**：本线不碰引擎代码与科学判据；机制变更走"设计稿 → 所有者核 → 公告"（§六）。

## 一、为什么有这套机制（一句话）

5+ 会话并行（本地/内评/联网/云端/所有者）共享同一工作树与同一块板——
**协作机制是项目的基础设施，不是行政装饰**。它的每一处条款都对应一起真实事故（见 §五痛点对照）。

## 四、核心流程图

### 4.1 发言（零号规则 · 带锁 7 步）

```
                ┌────────────────────────────────────────────┐
                │  board_post.py 一键执行（或手工照此顺序）      │
                └────────────────────────────────────────────┘
  fetch/pull --ff-only ──► 取锁(acquire) ──► 重读板尾 ──► 追加(只追加,UTF-8无BOM)
        │ 失败:分叉,人工处理      │ 他人活跃锁:等待(rc=2)
        ▼
  路径限定 commit ──► show --stat 核文件数=1 ──► push ──► ls-remote 对账 ──► 放锁(release)
                                                          │ 失败:rc=3,提交留本地
                                                          ▼
                                              pull --ff-only 后**重跑脚本**(幂等,不重复上帖)
```

**三条判定**：未 push 不算发言 ｜ 云端同样适用 ｜ 无法 push 时帖尾标"待推送——请`[本地开发]`代推"。

### 4.2 任务派发与承接

```
fish/所有者 ──派工包(docs/tasks/)或板帖──► 承接线：开工前必读板尾(§3.3-5)
                                              │
                                              ▼
                                   确认无跑批/锁冲突 → 执行 → 回帖(带证据标签)
新会话承接 ──► onboard.py 生成开场提示词（角色/基线/必读清单/第一步）
```

### 4.3 机制变更（不许静默改流程，R61 精神）

```
设计稿(板上发) ──► 所有者核 ──► 公告(板帖 + AGENT.md/README 同步) ──► 生效
     │                                                        │
     └─ 涉及工具: 先带测试过审（tests/ 全绿）                    └─ 未公告的变更不具约束力
```

### 4.4 板面维护

```
发帖后 >150KB ──► 任何成员可归档：总结 → 结论入路线共识 → 未决移植新板
                  → 旧板移 _share/archive/ → 登记 _archive/归档记录.md（R115）
日常保健 ──► board_check.py check（大小/署名/时钟/置顶/锁/断链/F-R24）
```

### 4.5 置顶区（M12，T-6；fish 2026-09-17 指示）

```
讨论板.md
┌──────────────────────────────────────────────────────────┐
│ <!-- PIN-BEGIN -->                                       │  ← 受控区块
│ > 📌 置顶区（维护：[所有者]｜更新于 YYYY-MM-DD HH:MM）      │    只允许所有者改
│ > 1. 跑批中：…  2. 待裁定：…  3. 待核阅：…  4. 期限：…      │    上限 5 条 / 2KB
│ <!-- PIN-END -->                                         │    超 7 天未更新 → 体检预警
├──────────────────────────────────────────────────────────┤
│ （以下照旧：只追加的讨论正文）                                │  ← 谁都可追加
└──────────────────────────────────────────────────────────┘
写操作 ──► board_pin.py set/add/remove（走写入锁；块外字节不变）
发言   ──► board_post.py 自动识别置顶块：只追加正文，置顶原样保留
```

**规则**：
1. **只允许 `[所有者]`/fish 维护**置顶内容（工具会提示；变更走公告）；
2. **上限 5 条 / 2KB**——超过报错（防置顶区自己成为新的膨胀源）；
3. 每条的写法："谁/什么事/期限"一行讲清；**过期即删**（体检报"已 N 天未更新"）；
4. 置顶区**不承载裁定记录**（那在 `路线共识.md`），只放"当前要事"；
5. 技术保障：块外内容字节不变（`split_board()` 切分），因此**置顶机制不与"只追加"纪律冲突**。

### 4.6 团队记忆（M13，T-7，fish 09-19 批准）——四条制度条款

1. **L0/L1/L2 分层**：`docs/记忆索引.md`（L0 指针，≤4KB 每周刷）→ L1 结构化摘要（路线共识/待办/实验记录/教训库，条目带编号+时间戳+出处+**状态**）→ L2 全文（板+归档）；**只发板不落索引 = 流程未完成**。
2. **结构性文件限权**：置顶区 / 路线共识 / 待办 / 记忆索引 —— 他人发现过期或错误 ⇒ **上板提醒，不代改**（本线 09-19 对置顶区即照此办理）。
3. **记忆写入锁**：写 `~/.workbuddy/`（用户层）或 `.workbuddy/memory/`（工作树层）前，取与 `_share/` **同一把锁**（`share_lock.py --slot <你>`，TTL 900s）——底层记忆已实测**跨会话/跨项目共享**（设计稿 §四）。
4. **归档前检查单**（4 项）见 `AGENT.md` §3.3.6 + `collab-toolkit/templates/归档前检查单.md`；**冷启动最小路径** = 置顶区 → 状态快照 → 未落定项（筛自己）→ 交接包（`onboard.py`）→ 板尾 3 帖。

## 五、协作成本度量（T-4 草案；回应 P4"治理膨胀"）

> 外部批评（元宝 2026-09-17）：5 天 110 条裁定 / 38.7KB 章程 / 11 项检查——**流程成本 vs 收益缺度量**。
> 回应方式不是砍机制，而是**先把成本量出来**，再按数据决定去留。

### 5.1 指标定义与当前基线（`board_check.py metrics` 实测，2026-09-17 22:38）

> ⚠️ **括号注**：22:4x 讨论板发生**第 4 次归档**（内评执行，§3.3 规则 1），板面重置为 ~20KB
> ⇒ "当前板大小/板增长速率"两项需按下一次度量重取；**裁定密度/事故率**为累计量，不受归档影响。

| 指标 | 口径 | 基线（项目 6 天） | 警戒阈值（建议） |
|------|------|------------------|------------------|
| **裁定密度** | 去重 R 编号数 / 项目天数 | **114 个 → 19.0 个/天** | >10/天 持续 3 天 ⇒ 启动瘦身评审 |
| **板增长速率** | 当前板 KB / 项目天数（归档后重置，偏低） | **22.4 KB/天**（归档前口径） | 单文件 >130KB 预警（已有） |
| **事故率（代理）** | 去重 F-* 编号数 / 项目天数 | **29 个 → 4.8 个/天** | 同型事故 ≥2 次 ⇒ 机制化防呆 |
| **_share 提交频度** | `git log -- _share/` 按日 | 09-13:39 / 09-14:9 / 09-15:35 / 09-16:32 / 09-17:9 | 观察项 |
| **单事项处理时延** | 提案帖 → 裁定帖 的时间差 | 暂无自动化（人工抽样） | 草案：抽 10 个 R 编号量中位数 |
| **各线等待时间** | 请求帖 → 被响应 的时间差 | 暂无自动化（人工抽样） | 草案：按角色分组量中位数 |

### 5.2 怎么读这些数字（诚实声明）

- **裁定密度 19/天 确实高**——但其中大量是"立规期"一次性裁定（R1–R30 多为基础设施）。
  判断标准不是绝对值，而是**趋势**：立规期结束后应自然下降；不下降才说明治理膨胀。
- **事故率 4.8/天 是上限估计**——F-* 编号含"环境缺陷"（F-R10/F-R15/F-R24 等不可修项），
  不全是流程事故。细分（流程/环境/仪器）是 v1.1 的改进点。
- 时延类两指标暂靠人工抽样（口径已预注册在本文，防"事后挑数"）：
  从路线共识倒序取 10 个 R 编号，在讨论板定位其提案帖与裁定帖的时分差，报中位数。

### 5.3 度量纪律

1. 度量报告**按月**或**按阶段**发板，不逐日刷板（防度量本身成为噪音）。
2. 任何"砍机制"提案必须附：该机制防住过的事故清单（反事实）+ 成本数据。
3. 新增机制必须附：它防什么事故 + 它的执行成本估算（秒/次）。
