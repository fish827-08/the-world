## 二、根因诊断：为什么成员总不按规则

### 🔴 根因 1：`AGENT.md` **根本不在 git 里**（主因）

```
the-world/AGENT.md          ← 不在任何仓库（the-world 不是 git 仓库）
_gitee_review/AGENT.md      ← 在仓库里（main 分支）
```

两份**靠手工复制同步**。只要有人只改一边，就产生分叉。
**今天的实际事故**：`AGENT.md` 被旧基点覆盖、丢失 18 行（含 §7.1.1）——正是这个结构的必然产物。

> **一份文件两个家 = 必然漂移。这是今天所有"不按规则"的源头。**

### 🔴 根因 2：主工作树本身就是陈旧副本

`digital-life-sphere/`（真身仓库的主工作树）停在 **detached HEAD @ `b896cc1`（09-08）**。
任何人在该目录打开项目，看到的都是**两周前的代码与章程**。项目章程 §6 反复警告"陈旧副本"，**而最大的那份陈旧副本就是仓库自己的主工作树**。

### 🟠 根因 3：双远程 + upstream 指错

- 两个远程（gitee / github），**GitHub 已落后 59 提交**
- `main` 的 upstream 指向 GitHub ⇒ 默认推送方向与实际工作流相反
- 成员对"哪个是真远程"认知不一致

### 🟠 根因 4：分支命名与生命周期无管控

- `feat/*` 与 `feature/*` **两套前缀并存**
- 17 个远端分支，**无一份"谁在用什么、什么时候合、合没合"的账**
- `collab/main` 落后 100 提交仍在（R9 已裁定取消镜像，分支却没清理）

## 三、目标架构（按所有者指示）

> 所有者指示：**the-world 目录作为 main；其他文件夹对应不同分支；切分支时文件夹内容随之变化。**

### 3.1 技术选型：**git worktree**（这正是"文件夹 = 分支"的标准实现）

```
the-world/                        ← 仓库真身 + 主工作树（main 分支）
├── .git                          ← 真身（由 digital-life-sphere/.git 上移）
├── AGENT.md                      ← ✅ 唯一一份，受版本控制
├── _share/  _eval/  _web_eval/  _roadmap/   ← ✅ 协作层，入 git
├── _gitee_review/                ← 引擎主工作区（main 分支的子目录）
└── _wt_<branch>/                 ← worktree：一个分支一个目录
```

效果：**切分支 = 切换文件夹**，不同分支的文件夹内容天然不同——与所有者描述完全一致。

## 四、分支管控纪律（即刻生效，写入 `AGENT.md` §十）

1. **开分支须有充分理由**：必须在讨论板说明「分支名 / 目的 / 关联任务号 / 预期合并时间」，**未说明理由的分支一律删除**
2. **分支命名统一 `feat/<短名>`**，禁用 `feature/`（历史分支保留）
3. **完成任务后由负责人主动发起合并请求**，在讨论板发帖，由**裁定者（所有者）审核后合并**
4. **合并后 24 小时内删除分支**（本地 + 远端），防再次出现 17 分支无人管的局面
5. **一个分支一个 worktree 目录**，不在同一工作树反复 checkout（防"陈旧副本"）
6. **引擎代码只走分支；协作文档（`_share/`）在 main 上直接追加**，不再开文档分支
7. **唯一活跃远程 = gitee**；GitHub 的处置待所有者裁定（同步 / 只读归档 / 废弃）

### 🔴 事故与修复：`git worktree prune` 误删主工作区登记（23:35）

**经过**：删除 `_collab_wt` 后执行 `git worktree prune`，
该命令**连带删除了 `.git/worktrees/_gitee_review/` 整个目录**——因为 `_gitee_review` 此前被 git 标记为
**`prunable`**（`worktree list` 里能看到该标记，当时未深究）。

**后果**：`_gitee_review`（**唯一活跃工作区**）瞬间失去 git 身份：
`fatal: not a git repository: .../.git/worktrees/_gitee_review`，无法执行任何 git 命令。
`git worktree repair`（无参 / 带路径）均失败。

**修复**（未丢失任何数据）：
1. commit 对象都在 `.git` 对象库里，不会因 worktree 登记丢失而丢失
2. 手动重建 `.git/worktrees/_gitee_review/`：`gitdir` / `commondir`(`../..`) / `HEAD`(`ref: refs/heads/main`)
3. `git reset` 重建 index（**不带 `--hard`**，工作区文件不动）
4. 验证：`HEAD=main`、`59b4ee1`、`git status` **clean**、与 `gitee/main` **0/0**、`fetch` 正常

**教训（已写入纪律）**：
> **❌ 全员禁用 `git worktree prune`**（无参更危险）。它会连"被标记 prunable 但仍在使用"的工作树一起清掉。
> 需要清理时用 `git worktree remove <路径>` 指定删除，或执行前先 `git worktree list` 确认哪些是 prunable 且确已废弃。
