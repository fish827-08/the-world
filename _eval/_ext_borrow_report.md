## 〇、一句话结论

**该 issue 的"归因层"基本正确、且在若干处比它自己以为的更正确（我们已把它当自评读过）；但它的"解药层"是错的，且其经验前提被它自己的姊妹报告推翻。**

- 它建议的 P0（指称博弈）**不是新东西**：等于我方 `docs/外来参考线/_advice/设计建议-20260912.md` §3.1 的"Lewis 化"，我方已在 **R28 明确"暂缓"**（理由：与 C3 自变量污染风险）。issue 版本比我们自己的规格**更粗糙**（缺收益量级前置判据、缺与 C3 的区分表、无生态接地）。
- 它的因果前提"think-chain-life 之所以能涌现 v3/v4 语言，本质是指称博弈给发射创造了直接选择压"**被它自己的 IKFJJ3 报告与对方代码共同证伪**：v3（其最可复现的结果）**根本没有指称博弈**（`environment.py` 零命中），v4 才引入隐式指称奖励，v5 引入显式指称博弈后**同口径指标反而下降**（0.061 < 0.183）。
- 真正值得借的是它的**方法论副产品**：结构破坏型零模型（Permuted）、Topographic Similarity、"任何语言指标必须报随机基线"的判别力检验。这三条恰好补我方 F-D3（全仓零统计推断）。
- 结论：**P0 指称博弈应拒绝（或最多降级为"仪器阳性对照"）；Permuted 零模型 + Topographic Similarity 应采纳（P1）；符号序列应延后并改写方案。** 详见 §七。

## 一、指称博弈 vs 我方 oracle：2×2 对比

### 1.1 核心 2×2（行 = 收益归属侧，列 = 设计）

| | **oracle**（已实现，R39/D-8） | **指称博弈**（tcl v5+；issue 建议的形态） |
|---|---|---|
| **发送者(S) 何时获益** | 仅当"某接收者踩着有信号的格**且该格有食物**"（`require_food=True`）时，按 `_id` 归因到发送者，由**接收者**转出 ≤`donation=0.05`；终身封顶 `0.1×自身累计发射次数 − 累计已获回馈` ⇒ **期望净收益 ≤ 0，只补偿不补贴** `[代码: simulation/oracle.py:26,52-93; simulation/sphere_engine.py:1362,1376-1384]` | 环境每 12 步**自动配对**同族群 S/R 并放置 3 个虚拟候选物，目标是环境随机指定的 1 个；接收者 18 步内走到目标 ⇒ **双方各 +6**；另有"S 指称过的食物被别人采到 ⇒ S 再得 0.5×奖励" `[代码: environment_v5.py:153-217,219-233,483-486,645-649]` |
| **接收者(R) 收益** | 落点有食物 ⇒ 正常进食收益（本来就有）；回馈是 **R 付给 S** 的 `[代码: sphere_engine.py:1388-1394]` | 到目标 **+6**（另加普通进食 `+0.1×gain`）`[代码: environment_v5.py:508,523]` |
| **信号是否必需**（R 有无别的信息源） | **不必需**。食物在 R 的感知邻居里直接可见（`fr = food_ratio[nb]`）；信号携带的 `f_bit` 只是同一量的**量化滞后副本** ⇒ 信号边际信息价值 ≤ 0 `[代码: sphere_engine.py:846,857-859,692-701]` | **对该 +6 通道必需**：目标是环境随机抽的，`★目标` 平面**只进发送者观测**（`if is_sender:`），R 无其他途径知道哪个是目标 `[代码: environment_v5.py:354-356,203-204]`。但**生存/觅食通道不依赖信号**（候选物是临时 dict，不是真实食物/能量实体）`[代码: environment_v5.py:183-217]` |
| **内容是否相关** | **刻意内容无关**：只看"该格有无任何 pattern"（`had_signal`），不看 pattern 值 `[代码: sphere_engine.py:774-777,1362]` | **内容相关**：+6 只在"解对了被指称的那个目标"时发放 `[代码: environment_v5.py:219-233]` |
| **生态嵌入度** | 域内、**能量守恒**（S→R 转移，`Σenergy` 不变）`[代码: oracle.py:73]` | **域外**：候选物与 +6 都是抽象奖励，不进入能量/捕食/食物网 `[代码: environment_v5.py:183-217 + 全局搜索 candidates 未被 append 进 self.food]` |
| **设计目的** | **仪器校准**（"在选择肯定存在时，我们的仪器能不能测到选择"）`[文档: simulation/oracle.py 模块 docstring]` | **任务注入**（给 RL 一个可学的通信任务）`[文档: tcl README v5 节]` |

### 1.2 关键差异 3 条（这 3 条决定了"能不能迁移"）

1. **指称对象是否对接收者不可观测**：oracle 的指称对象（食物）R 自己看得见 ⇒ 结构性零信息价值；指称博弈的指称对象（随机选中的虚拟候选）R 看不见 ⇒ 信息价值由构造保证为正。这不是"参数差异"，是**世界结构差异**（与我方 `docs/外来参考线/_advice/设计建议-20260912.md` §3.3"私有信息"同一诊断）。
2. **付费挂在"发射"还是"做对"**：oracle 付费挂在"R 恰好获益"上，且**内容无关**；指称博弈付费挂在"R 解对内容"上。我方广播信道建议 §1.1 的原话是"**收益挂在'做对'上，不挂在'发射'上**"——issue 的建议方向与之一致，但它没说清"做对"需要一个**不可观测**的参考量。
3. **奖励来源**：tcl 的 +6 是 RL 的 reward，不是能量；我方引擎没有 reward 通道，任何收益必须落到能量或繁殖。tcl 式 +6 在我们要么变成"凭空注入能量"（破坏能量守恒 → 生态门风险），要么变成"S→R 转移"（那 S 净亏，退化成 oracle 的加强版，仍无正选择压）。**这是 issue 完全没提的最大工程量。**

## 二、把"指称博弈"接进我方引擎：代价与风险

### 2.1 新增实体 / 位置（"候选目标集合"从哪来）

| 方案 | 代价 | 结论 |
|---|---|---|
| **A. 照搬 tcl：虚拟候选物 + 外部任务** | 需要：新实体层（3 个候选物/对）、每 agent 任务状态（`sender/receiver/target/deadline/success`）、环境定时配对器、**观测掩码**（★只给 S）——但我方决策是 `score→softmax→选邻居格`，没有"候选物"概念，也没有 per-agent 观测掩码；还要一个"抽象得分"通道 | 改动量 ≈ 新增一个小型环境子系统（类比 tcl `environment_v5.py` 的 500 行级），且**必须在引擎主循环里加第二套并行状态机**。`[推断]` |
| **B. 域内版：私有信息 + 共享收益**（我方自己的 A-4/§3.1/§3.3 规格） | 只需给资源场加一个"只有站上去才感知到"的隐藏位（如斑块富集度），把该位进 `state`、进 `codebook`，并给 S 一条"R 采到该格 → S 也得分"的耦合项 | 改动面小一级，且不动能量守恒（共享收益可做成"R 采到的能量分 S 一部分"）`[文档: docs/外来参考线/_advice/设计建议-广播信道与共享收益-20260913.md §1.1-1.4]` |
| **C. 用现有 patch 当候选集**（`patch_count=30, patch_radius=2`） | 我方资源斑块对 R 直接可见（`fr`），必须先让 R"看不见"才成立；否则回到 oracle 式零信息 | 不解决根本问题 `[代码: 资源场对感知可见]` |

**关键事实**：tcl 的候选物是**临时 dict**，不是食物实体（不进 `self.food`），观测里只通过"目标平面"出现且只给 sender `[代码: environment_v5.py:183-217,243,354-356]`。也就是说**它的指称对象是纯抽象标记**——这直接解释了为什么它能"干净地"制造信息不对称：因为它压根不在生态里。我们要复刻，就得同样造一个"不在生态里"的通道。

### 2.2 要不要改 `signal_field` 的数据结构？

- **不必须改 dtype/形状，但必须改"state 的定义"**。当前 `pattern` 只由发送者自身状态决定（`state = e_bin*4 + f_bit*2 + n_bit`，`e_bin = energy/max_energy*4`），**与任何外部指称对象无关** `[代码: sphere_engine.py:692-701]`。要让信号指代目标，必须把"目标索引"并入 `state` 或另开一位。这是**语义改动**，不是容器改动。
- `_marks` 是 `(n_cells,) uint8`、16 种有效 pattern（低 4 位）`[代码: world/signal_field.py:9,39,49]`；若目标数 ≤16，**容器够用**；若要"序列"，才需要扩容器（见 §四）。

### 2.3 会不会破坏"双路径逐位对拍"（Rust/Python）？

- **会，除非把新机制显式钉成 Python-only 并加"静默忽略就报错"的门槛。** 现成先例正是 oracle：`C-8` 在 `use_sim_core=True` 且 `oracle.enabled=True` 时**直接 raise**，理由是"静默忽略会重演 R14『配置看似生效实则没生效』" `[代码: sphere_engine.py:310-315]`。
- 现有 D2 的门槛是**局部的、易漏的**：发射段只在 `arbitrary_codebook` 时回退 Python `[代码: sphere_engine.py:668-670]`；移动段只在 `perception_radius==4 / noise>0 / softmax_tau>0` 时回退 Python `[代码: sphere_engine.py:729-731]`。**新增任何一条"D2 语义"都要在每一处都补上**，否则会出现"发射走 Rust 旧编码、接收走 Python 新语义"的混合路径（这正是 F-R9/R59 的同型事故：配置穿过 CLI→grid→preset→`--arm`→引擎开关→运行时路径六层，每层可静默丢弃）`[文档: _share/路线共识.md R65]`。
- Rust 侧 `signal.rs` **把编码硬写死**：`pattern = e_bin*4 + f_bit*2 + n_bit`，签名收 `(n_cells,) u8 / (n_cells,) i32` `[代码: sim_core/src/signal.rs:33-46,69-88; sim_core/src/lib.rs:856-878]`。要让 Rust 跟上，必须改内核 + 函数级对拍 + 引擎级对拍；不跟上就必须加 config 门（见上）。
- 结论：**双路径不是技术上不可保，而是"契约成本"高**：每一个新机制都要（i）写 Python-only 门 + 显式报错、（ii）写不变量测试、（iii）在 manifest 里记录开关（否则 provenance 不可解析，R31/R38 硬门不过）。

### 2.4 会不会影响生态门（刚验证 10/10 过门）？

- **会，且是硬影响。** 生态门（N 稳定 >0 持续 50k）是**当前适应度景观**的性质；指称博弈要往世界里加一个"与生存无关的第二收益通道"，等于改适应度景观 ⇒ 该批 10/10 的结论**对新配置不再适用，必须重跑**。参照 R36：生态门通过只对**那一批**保留为独立结论。
- 具体风险两条：
  1. **能量守恒 vs 能量注入**。oracle 选择 S→R 转移（守恒）`[代码: oracle.py:73]`；tcl 式"双方 +6"若要守恒，只能 S 掏钱给 R ⇒ S 净亏 ⇒ 需要额外的"共同收益"来源，否则 g15 只会更快被淘汰（我方广播信道建议 §3.4 冲突 2 已写死：**先接回报通道，再谈扩信道**，否则"成本↑+收益仍为 0 ⇒ 只会加速 g15 灭绝"）`[文档]`。
  2. **饱和混淆**。我方种群常态顶到 `max_count=5000` / 7200 格（R32 已把饱和列为受控变量，R41 把"不饱和"列为默认）。新增收益通道会**加快饱和**，从而把 g15 的判读重新推进"饱和臂 vs 捕食主导臂差一个数量级"的方差陷阱 `[文档: _share/路线共识.md R44]`。

## 三、最关键的批判：L1/L2 会不会变成"按构造必然成立"？

**我的判断：分三级，答案不同——L1 变成"任务成功率"，L2 变成"不可观测指称的副产品"，L3 变成"按构造必然"，而 L4 被反向阻断。合起来：这会把"涌现"问题替换成"任务求解"问题，结论可外推性大幅下降。**

### 3.1 L1（信号携带信息）——不是逻辑必然，但不再是"涌现"

- 严格说 **MI>0 不是按构造必然**：接收者可以乱猜（tcl v6 随机策略的"组合解码"达 0.85，说明指标本身可能虚高）`[文档: tcl README v6/v8 节]`。所以指称博弈**不会**让 L1 变成恒真命题。
- 但它把 L1 的语义从"信号系统自发出现并携带环境信息"改成"**被试在人为任务上达标**"。任务、目标分布、奖励全由设计者给定 ⇒ L1 的通过只证明"我方的遗传+启发式决策机制能解一个通信任务"。
- 我方 L1 的定义是"信号↔环境/上下文 MI **显著高于漂变零模型基线**"`[文档: _share/战略定位-20260912-语言涌现可达性.md L0-L4 表]`。注意后半句：**判据本来就要求零模型对照**。所以即使在指称博弈里，只要老老实实跑 `signal_disabled` / `neutral` / `permuted` 三臂，L1 仍然是一个**有判别力的测量**——它测的是"我方机制的能力上界"，不是"语言涌现"。**这是这个实验唯一站得住的用途（阳性对照/仪器校准），前提是措辞上不许写成"涌现"。**

### 3.2 L2（任意性）——会变成"按构造必然"

- 任意性判据是"能指与所指解耦、非物理相似"。若指称对象对接收者**结构性不可观测**，那么从接收者视角看，任何一致的映射**都不可能**由物理相似性推出 ⇒ **任意性由世界结构保证，而不是被选择出来的**。
- 但注意一个真实的反例：tcl v4 反而长出了**描述性/象似性编码**（sender 看得见目标颜色 ⇒ sym1 系统性编码颜色，MI 0.399）`[文档: tcl README v4/v7]`。也就是说指称博弈首先给的往往是**象似**，不是**任意**；任意性还需要**瓶颈 + MDL 紧凑性偏差**才会成为被选择项。这恰好落在我方 **W-F3（MDL 紧凑性偏差实质缺失）** 上：**先补 W-F3，L2 才可能从"不可能"变成"被选择"；不补，L2 只会变成"因为接收者看不见，所以映射必然任意"的平凡结论** `[文档: _web_eval/FINDINGS.md W-F3; _share/评估-时间表与涌现概率-20260913-2212.md L2 行]`。
- 换句话说：issue 的建议**跳过了它自己该依赖的前提**。补 W-F3 + W-F4 才是我方文档认定"唯一最大杠杆"（R70），而 issue 只字未提 W-F3/W-F4。

### 3.3 L3（组合性）——如果照 tcl v6 的"单维度不可解"设计，就是按构造必然

- tcl v6 的做法是**人工保证**"目标与至少 2 个候选同色、至少 2 个同形 ⇒ 任何单一属性维度都无法唯一确定目标，只有组合才行" `[文档: tcl README v6 节]`。这是把"组合性必须出现"写进任务约束 ⇒ 一旦达标，**组合性是任务设计的重言式**，不是涌现。
- 更强的反证来自对方自己的 v8：消息被随机 permutation 后，**组合性指标反而更高**（0.246 > final 0.054）`[文档: tcl README v8 表]`。即：他们的组合性公式对"消息-语义脱钩"不敏感 ⇒ 在"按构造必然"的场景里，连指标本身都不可信。
- 所以我方 L3 若要碰，**必须同时上结构破坏型零模型**，否则结论不可外推。

### 3.4 L4（语义接地 / 可撒谎）——指称博弈（外挂版）会**反向阻断**

- 域外虚拟目标没有生态后果，符号指向的是一个"任务索引"而非世界状态。要"可撒谎"，必须存在**利害**（撒谎有收益、被抓有代价）`[文档: L4 判据]`。
- 因此：**为了把 L1-L3 做漂亮而注入域外任务，会把 L4 推得更远**。这是权衡上的反向激励，issue 没做这个取舍分析。

### 3.5 小结（可直接写进预注册）

> 指称博弈臂的产物只能表述为：**"我方引擎在人为通信任务上的可解性上界" + "L1/L3 仪器判别力的校准"**。
> 不得表述为"语言涌现""信号演化""任意性涌现"。这与 R30 的措辞纪律同构（g15 高 ≠ 语言涌现）`[文档: _share/路线共识.md R30]`。

## 四、"符号序列"建议是否成立？

### 4.1 先核实 issue 的那句话

> issue 原文："信号是单格单 uint8（16 模式），多发射者覆盖写，符号串数据结构不存在"

**核实结论：准确。** 逐条给行号：

| 声称 | 代码事实 | 判定 |
|---|---|---|
| 单格单 uint8 | `self._marks = np.zeros(world.n_cells, dtype=np.uint8)` `[代码: world/signal_field.py:39]`；模块 docstring："uint8 低 4 位（bit0~bit3 对应 4 个子格）" `[代码: world/signal_field.py:9]`；写入时 `pattern & 0x0F` `[代码: world/signal_field.py:49]` | 成立（更精确说：**uint8 容器，实际只用低 4 位**） |
| 16 模式 | `write()` 只保留 4 位 ⇒ 0-15 `[代码: world/signal_field.py:44-50]` | 成立 |
| 多发射者覆盖写 | `write_many` 用花式索引赋值 `self._marks[cells] = p` ⇒ **重复索引取最后一次**，无累积/无合并 `[代码: world/signal_field.py:52-58]`；Rust 侧同语义且**注释明写**"多 emitter 同格：按循环顺序后写覆盖先写" `[代码: sim_core/src/signal.rs:13,88-90]` | 成立（且双路径一致） |

### 4.2 但"改成序列"在我方引擎里有两个它没算到的拦路虎（都为 `[实测]`）

**(1) 信道已经饱和，"有没有信号"几乎不携带信息。**

### 4.3 最小改动面（比 issue 想的大，但有一条捷径）

| 做法 | 改动面 | 与"逐位对拍/快照"的冲突 |
|---|---|---|
| **按 issue 原意**：相邻多格串读（cell 0 → cell 1 → cell 2 当词元序列） | 发射端要**顺序写多格**；但每格都可能被第三方覆盖 ⇒ "串"会被污染。要么引入写入锁（并发语义全变），要么接受噪声 | 🔴 高：并发写入语义、RNG 顺序、快照（`_marks`/`_age` 均须扩维+版本升级）、Rust 内核重写或强制 Python-only |

| **零新容器捷径**：把现有 4 个 bit 重新解释为"时间序 4 槽移位寄存器"（词内结构，docstring 已提"田字格 4 位置提供词内结构" `[代码: world/signal_field.py:7]`） | 不用改 dtype/形状/快照/Rust 签名 ⇒ **双路径与快照零冲突** | 🟢 低，但**语义冲突**：现有 4 位是"能量2+食物1+邻居1"的并发状态位，改成时间序就废掉了现在的语义，必须作为**新条件（C6 类）预注册**，不能声称"没改 C1" |
| **先解决覆盖写与饱和**（我方广播建议 §6.3 的方案）：每 pattern 一条通道 `loudness[p,c]`，接收者按 `w_p` 竞争抽样（"谁最响听谁"），归一化而非求和 | 新容器，但**确定性、counter RNG、可并行** `[文档: docs/外来参考线/_advice/设计建议-广播信道与共享收益-20260913.md §6.3]` | 🟡 中，但这是**唯一不会在满员球面上饱和**的方案 |

**结论**：issue 的"P1 符号序列"在**数据结构层**成立（"没有符号串"是事实），但在**工程与生态层**把顺序搞反了——我方自己的评估已写死："广播（扩信道）改变的是'谁能收到'，不改变'发送者为什么要有回报'；先扩信道 ⇒ 成本↑收益仍 0 ⇒ **只会加速 g15 灭绝**" `[文档: 同上 §3.4 冲突 2]`。序列化是"扩信道"的一种，**必须排在"回报通道"之后**。

### 5.2 "无信息不对称（D2 前感知半径 8 > 信号半径 1）"

- **括号里的机制描述错误**：信号写在**发射者自己所在格**（`self.signals.write_many(e_flat, patterns)`，`e_flat = self._flat[emitters]`）`[代码: sphere_engine.py:687,709]`；读取发生在**接收者的整个邻居集** `nb`：`sp = sig_present[nb]`、`nb_sigs = self.signals._marks[nb]` `[代码: sphere_engine.py:847,864]`；Rust 移动路径同样收到 `nb_table` + `signal_marks` `[代码: sphere_engine.py:767-771]`。⇒ **信号的读取范围 == 食物感知范围**，不存在"信号半径 1 < 感知半径 8"。
- 更根本的是：`perception_radius` **不是欧氏半径**，而是**邻居集基数**（8=Moore 全邻，4=Von Neumann 正交邻）`[代码: simulation/config.py:264; world/sphere_world.py:255-279,281-306]`；`neighbors()` 返回 8 个相邻格、不含自身 `[代码: sphere_world.py:281-306]`。
- **但它的结论方向仍然对**，只是理由要换成更硬的三条：
  1. **内容冗余**：`state` 的 `f_bit` 是"发送者所在格资源 > 0.5×容量" `[代码: sphere_engine.py:696-699]`——而接收者在评估相邻格时**直接、当前地**看到同一个量（`fr = food_ratio[nb]`）`[代码: sphere_engine.py:846]`；
  2. **信号还更差**：信号是**滞后 ≤50 tick 的 1 bit 量化副本**（`duration=50`，`_age` 剩余寿命）`[代码: signal_field.py:27,39-40,50,72-78; sphere_engine.py:221]`，且要花 `SIGNAL_COST=0.1` `[代码: sphere_engine.py:682]` ⇒ 对 `f_bit` 这部分**信息价值 ≤0**；
  3. **唯一非冗余位（`e_bin`=他人能量档、`n_bit`=他人格的拥挤度）与接收者适应度无关**；且存在项已饱和（§4.2 实测：86-100% 个体邻居里有信号）⇒ 判别力趋零。
- **判定：机制声称错（读取范围不是 1 格），结论对（无信息价值），理由错位。**

### 5.3 "信号只是移动打分弱加分项（0.5 权重与食物并列）"

- **存在项：准确**。`score = perc*(fr*0.5 + sp*sig_weight) + soc*densities[nb]`，其中 `sig_weight = trust*(0.5 + rep_w*trust) ≤ 0.5`，即**存在项 ≤ 食物项** `[代码: sphere_engine.py:856-859]`。
- **但漏了两条信号相关通道，因此"信号只是弱加分项"是**不完整**的**：
  - **内容项** `score += 0.4*perc*interp`（`interp = _interpret[idx, pattern]`）`[代码: sphere_engine.py:864-870]` ⇒ 权重 0.4 = 食物项的 80%，且**per-pattern 内容相关**；
  - 记忆项 `0.3*perc*mem` `[代码: sphere_engine.py:860-863]`。
- 因而"无内容通道"这个推论是错的：**内容通道存在且权重不低**；真正的病根不是权重，而是**payload 冗余 + 信道饱和 + 字母表塌缩（94.2% 集中在 `e_bin=3` 的 4 个 pattern）** `[实测 §4.2]`。
- **判定：数字对，定性偏（"信号只是弱加分项"低估了 0.4 权重的解读表通道）。**
