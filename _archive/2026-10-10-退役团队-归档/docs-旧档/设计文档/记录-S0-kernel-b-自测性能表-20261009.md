### 二·补 计时口径为什么会差 2～2.4 倍（本笔最要紧的一条方法论）

同一 seed、同一装置，**同一进程内连跑**的 `ms/tick` 中位是 **14.5～18.8**（首轮冷启动 6.9～7.7，
随后逐轮抬到 15～19），而**行为逐位相同**（`pop`、`cap_hits`、digest 三轮完全一致）。
⇒ 涨的是解释器/内存侧的自身污染，不是模拟内容。chain 脚本 `tools/s0_batch_chain.py` 本来就
**逐 run 起独立进程** ⇒ 机时规划认 fresh 那一栏（1.1–1.3 h）；若谁改成"一个进程里连跑 32 个 run
取中位"，会**凭空多算一倍机时**、还可能把"变慢了"当成行为变化。脚本保留 `--mode inproc` 只为把这个
坑显式摆出来对比，`fresh` 是默认。

## 三、四条读法（给 PI 排期用）

1. **成本随人口，不随格数**：纯 py 逐个体循环 ⇒ `max_ind` 2000→5000 让 ms/tick 从 7.29 涨到 9.93，
   而格数同为 28,800 ⇒ 想压机时只能压 `max_ind`／人口，扩网格几乎免费。
2. **本机 32run 串行 ≈ 1.09–1.30 h**（正式档 fresh 口径）⇒ **落在"≤3h 本机档"内**，
   与 PI 板上"云 2 路 1.1–1.2 h"同量级；两笔各走各的码路（见 §一-2），不互推、不双写。
3. 🔴 **规模档把我的 [待裁] 装置水位差变成了可读信号**：正式规模下 `α_W=1` 支末人口 1969、
   `cap_hits=0`，`α_W=0` 支顶到 2000、`cap_hits=3984` ⇒ 频率项确实在压低规模；但 A 支
   `cap_hits=17962` 高得离谱 ⇒ 装置承载力实际是 `max_ind` 而不是资源，**`pop`+`cap_hits` 必须入册
   共同面**（PI 已按标注假设先行，判读口径候砚），否则"顶格拒绝噪声"会被读成效应。
4. 微型档 0.27–0.44 ms/tick ⇒ **单测继续用微型档**（15 例 <1s），正式规模只在 Pre-Flight/标定批起。
