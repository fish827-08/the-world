## 一、直接回答 `[联网]` 点的三个问题

### 1. `_id` 个体键的读取成本 —— **可 O(1)，但不要沿用 oracle 的解析方式**

- `_last_sender` **已是 per-cell int64 的 id 数组**（`sphere_engine.py:342`），发射时写 `_last_sender[e_flat] = _id[emitters]`（`:800`）⇒ 接收者拿 `_last_sender[cc]` 就是**发送者 id**，无需任何解析。
- 但 oracle 归因路径**每 tick** 做一次 `np.unique(self._id, return_inverse=True)`（`:1471-1475`）把 id 映回槽位 —— 这是 **O(P log P) 的排序**，属**已有成本**，声誉机制**不必**沿用它。
- **建议**：声誉存储用**id 键控账本**（照现成模式 `_grow_id_arrays`（`:1412`）+ `self._rs_children[self._id[ri]] += 1`（`:1305`）：**用 `_id` 直接作下标**，出生时扩行）。读取 = 查表 O(1)；**绝不用槽位索引**（死亡压缩会重排槽位 —— F-R16 / D-17 已付过学费）。

### 2. `trust` 能否复用为声誉载体 —— 🔴 **不能**

`trust` 是**接收者自身的标量**：
- 更新式（`:1014-1019`）：落在**真信号格** `+trust_true(0.05)`、**假信号格** `−trust_false(0.1)` —— 记的是"**我对信号整体的信任**"，与"是哪个发送者"无关；
- 用途一（`:942`）：`sig_weight = self._trust[idx] * (0.5 + rep_w * self._trust[idx])` —— 接收者**自己的信号寻求倾向**；
- 用途二（`:1276`）：亲子继承 `0.8×亲代 + 0.2×0.5` —— 遗传的是**个体的性状**，不是对具体他者的观察。

⇒ 用它承载"发送者 X 的声誉"会**三重语义冲突**（自身/他人、无个体键、遗传的是性状而非观察），且会污染既有判据。**必须独立存储**。

### 3. 工作记忆 1 槽改记"帮我者 id" —— 🔴 **高危，必须新开数组**

`_work_memory` 是 `(P,4)` 的**格位索引**，用法 `np.isin(nb, valid_mem)`（`:946-949`，判断"候选邻居格**是不是**我记住的富食格"），并整槽复制遗传（`:1327-1330`）。
若把 1 槽改存 id，则 `np.isin(nb, valid_mem)` 变成**格位空间与 id 空间混比** —— 两者都是小整数，**不会崩溃、只会静默出错**（**F-B4 同类**：索引空间混用的静默错误，`_eval/FINDINGS.md:22-28`）。
⇒ 用**独立** `_benefactor`（id 键控）承载，**不要复用工作记忆槽**。

## 二、🔴 一处**必须先裁**的设计矛盾：`[联网]` R-1 的"观察输入"与 R6 判据互斥

- `[联网]` §二.2 提议：**"oracle/门控的付款事件（`true_sig ∧ Δ_i>0`）天然是观察输入"**；
- 同帖 §四 又写：判据不变 = **"oracle 关、reputation 开时 g15 是否上升"（R6 形态）"**。
- ⇒ **两者互斥**：oracle 关 ⇒ **没有付款事件** ⇒ 声誉永不更新 ⇒ 在该判据下 C3 **恒惰性**，会产出"看似 C3 无效"的**假阴性**。

**解（须写成 C-2 前置裁定）**：把"**观察**"与"**付款**"解耦 ——
观察量 `true_sig`（`:999`，移动段本就已算）与反事实 `Δ_i`（`:971-988`，D-18 ⑥b 探针）**都不依赖 oracle**；
`_oracle_on` 只门控**转账**（`:1004-1013`），不门控观察。
⇒ R-1 应表述为：**观察事件 = "到达『有信号 ∧ 有食物』的格 ∧ Δ_i>0"，与 oracle 开关无关**；oracle 只作**仪器校准**，不参与声誉输入（这也保住 R100 条件 5：仪器与科学集互斥）。

**成本**：Δ_i 已在跑（C1a 实测 `resp_a_exposure=0.9984` ⇒ 近乎每次决策都算了 `score_wo` + softmax）⇒ 把 Δ_i 从"探针专有"提升为一等观测量，**边际成本 ≈ 0**（当前批次已在付这份计算）。

## 三、🔴 "假接线"风险：`reputation_weight` **不是**声誉

`config.py:282` 该字段自己的定义是：

> 移动得分中"信号项"随**自身 trust** 放大的系数：`sig_weight = 0.5 + reputation_weight × trust`

⇒ 它是**接收者自我信任的正反馈放大**，与"发送者声誉 / 间接互惠"**无关**。
⇒ 若按 R101 与外部报告的表述把"`reputation_weight > 0`"当作"C3 已接线"，得到的是**假接线**：不会产生"因为我帮过你、所以你对我更好"。
**建议**：C3 用**新字段**（如 `sender_reputation_weight` + `reputation_update`），`reputation_weight` 保留原名与语义（不动既有快照与判据）；并在文档里把两者显式区分。

## 四、顺带一条与 R113 的交叉（第二个阈值错位面）

信号 `f_bit` 编码用 `0.5×capacity`（`:782-785`），而**解读表的学习更新**用 `food_threshold = 0.3` 判定"该格有食物"（`:1030`、`:861`、`:998`）⇒
**编码器与学习器用的是不同谓词**：学习器把信号当作"这里有食物(>0.3)"的预测来更新 `_interpret`，而信号内容只在 >0.5 时才置位。
这是我 22:02 报的 F-M2（信号↔付款不一致）的**第二面**（信号↔学习不一致）。R113 删 `f_bit` 会顺手消掉它，
但**阈值单源化**仍应在 C3 接线**之前**做 —— 否则声誉若将来进信号内容（R-3），会再错位一次。
