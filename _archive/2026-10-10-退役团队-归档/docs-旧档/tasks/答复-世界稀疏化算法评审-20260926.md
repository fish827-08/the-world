## 一、先回答你们的 7 个问题（逐条 + 证据）

### Q1 `nb_table` 是每 tick 重建还是建一次？

**答：只构造一次（构造期预计算）。** 所以你们 §8.2 的"30 MB/tick 是灾难级"不成立。

**但真正的问题在别处，而且比你们设想的大 120 倍**：这张表在 480×960 下是 **3 539 MB**（不是 30 MB）。

原因：为把"统一步长"喂给 Rust，表被补齐到 `max(8, cols)` 列，而**极点行的邻居数是相邻纬度带整行（`cols` 个）**：

```python
# simulation/sphere_engine.py:571
nb_stride = max(8, self.world.cols)          # 480×960 ⇒ 960
self._nb_table = np.full((n_cells, nb_stride), -1, dtype=np.int64)
```

⇒ 内存 **∝ rows × cols²（二次）**：

| 世界 | 形状 | 内存 |
|---|---|---|
| 60×120 | (7 200, 120) int64 | 6.9 MB |
| 240×480 | (115 200, 480) int64 | 442 MB |
| **480×960** | (460 800, 960) int64 | **3 539 MB** |
| 960×1920（锚点族里更大的一档） | (1 843 200, 1920) int64 | **28 300 MB** ❌ |

⇒ 顺带一个**重要的负面结论**：**960×1920 在现架构下根本无法构造**（28 GB 单张表）。
锚点族里"世界更大"的档位，在修掉这条之前都不成立。

### Q2 Rust 是每 tick 调一次还是每体调一次？

**答：每 tick 一次，整批传数组。** 共 13 个调用点（`regrow` / `step_vectors_stage1/2` / `step_movement` / `consume_many` / `signal_emit` / `predation_and_culture` / `reproduce_batch` / `fruit_charge` / `eat_fruit` / `pleasure_update` …），全部传长度 N 的数组。

⇒ **你们怀疑的"最大的嫌疑点"不成立。**

### Q3 信号会不会向邻格传播？

**答：不会（`v_s = 0`）。** 机制是：每人每 tick 写 **1 个码到自己所在格**，接收者读自己邻居范围内的 `marks`；信号寿命 50 tick。

⇒ 你们定理 1 的前提 **A2 成立**，影响半径项 `v_s·(t−t_s)` 恒为 0。

### Q4 食物有没有横向耦合（扩散 / 邻域竞争）？

**答：没有。** 再生公式是

```
growth(cell, t) = regrowth_rate × clip((T(cell,t)+20)/20, 0, 1)^temp_sens
                × [light_sens>0 时的光照项]
                × patch_mult(cell)
```

**不含当前存量、不含任何邻格量**（`light_sensitivity` 默认 0 ⇒ 光照整块跳过）。

⇒ **你们的前提 A1 成立**——食物通道完全不在耦合图里。这条我们独立确认过两次（一次是解析、一次是从空存量实测长满曲线）。

### Q5 `T(cell,t)` 是否严格周期？只依赖纬度行？

**答：严格周期成立；但不只依赖纬度行。** 这会让你们 §5.2 的"情形 A"需要扩展（详见 §六.2）。

- `base_temperature` 只依赖纬度（全格永久缓存，与 tick 无关）✅
- 但 `temperature = base + 昼夜项`，而**昼夜项在经度方向扫掠**（固定太阳 + 世界自转）⇒ 实际依赖 `(row, col, tick)`
- 严格周期 = `lcm(rotation_period, season_period)`

### Q6 22 000 这个 K 在 480×960 上实测过吗？

**答：没有，是线性外推。** 我们的标定是 `K ≈ 3.67 × 产能格数`（在 60×120 上测的），480×960 + 480 斑块 ⇒ 6 032 产能格 ⇒ 外推 22 128。

**你们说得对，这是必须先实测的。** 我们在 §二.1 把它接受为第一优先。

### Q7 真实约束是单 run 延迟还是批吞吐？可用核数？

**答：我们自己之前也没把这个问题问清楚，你们逼出来了。** 现在是：

- **科学迭代**需要的是"**单 run ≤ 30 分钟**"（改一个参数、当天能看到方向对不对）
- **正式批**需要的是"**一批 ≤ 隔夜**"（6–48 run）
- 可用核数：本地开发机（单机多核）+ 云端实例（可横向加）

⇒ 你们说的"加核 + 批调度比稀疏化更划算"**只对正式批成立**；对"科学迭代"，稀疏化/优化的价值是把单 run 从小时级压到分钟级。**两个目标都要，优先级：先压单 run。**

### 2.1 R0-A（别把 K 一起放大）——**接受，并加一条量化准则**

我们接受"斑块密度是独立实验变量"，并补一条**可用于定档的设计准则**（它把"科学目标"和"性能"直接接上）：

> **准则：让「能量续航距离」≈「斑块间距」。**

- 续航距离 = `(max_energy / base_metabolism) × v_typ`（`v_typ ≈ v_max/2`）

这条准则的意义：它让"找食物"处在**刚好够得着**的位置（走到下一个斑块之前刚好耗尽），

**它同时把 K 和难度锚在了一起**——这正是你们 R0-A 想说的事，只是我们给了一个可算的落点。

⚠️ 但你们表里的"稀疏化后"列，**在你们自己的建议顺序下是拿不到的**：

## 三、🆕 我们新发现的两个结构性问题

### 3.1 邻居表内存 ∝ rows × cols²（并解释 J2 的"5.8 μs/个体"从哪来）

见 Q1。**这条直接影响你们的 R0-B**（§四），并且意味着：

> **在修掉它之前，"世界比 480×960 更大"的档位在架构上不成立。**

**它也可能是你们 J2 的一部分答案**：22 000 个体 × 每次邻居查询落在 7 680 B 行距之外
（≈ 每 1 000 个个体就换一页 TLB），这种访问模式在 C 侧是"看起来只是 gather"的代码，
实际是持续 TLB miss。我们建议你们在算 `b = 5.8 μs/个体` 的理论下界时**先把它排除**。

### 3.2 🔴 速度基因的量化坍缩（**这不是性能问题，是机制失效**）

这一条你们没有看到，因为它不在"稀疏化"的范围里，但它是我们当前尺度方案里最紧的约束。

**机制**：`subpos` 把位移量化为

```
steps = floor(speed × subdiv + 0.5)
speed = clip(g18(MOBILITY) × age_factor × speed_gain, 0, speed_cap)
```

⇒ 真实速度档位数 = **`v_max × subdiv`**（赤道处）。

**实测**（探针 `experiments/speed_quant_probe.py`，真实引擎、真实年龄结构）：

| 配置 | 可达档 | **实际占用档** | 顶格占比 | 零步占比 |
|---|---|---|---|---|
| 现状默认 `speed_max=2.0, gain=4.0, subdiv=4` | 9 | 5 | 50.0% | 21.6% |
| **只把 `speed_max` 压到 0.25**（gain/subdiv 不动） | **2** | 2 | **93.8%** | 30.7% |
| `gain` 也压到 0.25（让基因铺满量程） | 2 | 2 | 0% | **89.6%** ❌ |
| 再提 `subdiv` 到 20（量子 0.05） | 6 | **4** | 0% | **24.6%** ✅ |

**读法**：

- 只压 `speed_max=0.25` ⇒ **93.8% 的个体钉在上限** ⇒ 速度基因退化成"走/不走"开关，**选择压消失**
- 把 `gain` 一起压到 0.25（让 0–1 的基因铺满 0–0.25）⇒ 顶格消失，但**89.6% 的个体被量化成"0 步"**（量子 0.25 太粗）⇒ 更糟
- **必须同时把 `subdiv` 提到 20**（量子 0.05）⇒ 零步占比回到 24.6%，档位恢复正常

⇒ **结论：`v_max` 这个量不能单独设定，它和 `subdiv` 是一对的。**
`subdiv ≈ 4 / v_max` 是下限（保证平均个体不被量化成静止），推荐 **`subdiv ≥ 20 / v_max`**（保证 ≥5 档）。
这一条**直接改变了"世界该多大"的答案**（§五）。

## 六、R3（惰性求值）的实现细节

### 6.1 好消息：我们的休眠唤醒比你们假设的更干净

实测（`[实测]`，patchy 配置）：**斑块从空到全满 = 201 tick**（容量中位 78，起步速率中位 0.60/tick）。

⇒ 结合你们的 **clamp 可交换引理**（我们独立确认成立：`g_τ ≥ 0`，逐 tick 截断 ≡ 一次性截断）：

- **休眠 Δ > 201 tick ⇒ 唤醒时 `stock = capacity`，精确、O(1)**
- 而 201 tick 相对一昼夜（480–2400）很小 ⇒ **绝大多数唤醒走这条快路径**
- Δ ≤ 201 时才需要 `P(c,t)` 的增量

⇒ **你们的 `(t0, s0) + P(c,t)` 表示在我们这里可以简化成"快路径 + 短窗口线性积分"，
不需要为全量程建表。** 这比你们 §5.2 讨论的情形 A/B 都省。

### 6.2 一处必须改的前提：`T` 不只依赖纬度行

你们的"情形 A（最有可能是你们的情形）"假设 `T` 只依赖纬度行。
**我们的 `T` 含昼夜经度扫掠**（固定太阳 + 自转）⇒ 依赖 `(row, col, tick)`。

三个可能的处理（我们倾向第 2 个，请你们判断）：

1. **按 `(row, 经度相位)` 建表**：表大小 = `rows × cols × P_season`，480×960 下不可承受
2. **分离快慢两分量**（推荐）：`T = base(row) + 昼夜(row, col − sun(t))`，
   其中昼夜间**日平均后只依赖 row**；季节分量也只依赖 row。
   若接受"把昼夜并入解析积分"，则 `P(c,t)` 只依赖 `row` ⇒ 表大小 = `rows × P_season`（480 × 360 = 173 k f64 ≈ **1.4 MB**，与你们估计一致 ✅）
3. **先把 `light_sensitivity`/昼夜对再生影响设 0**（现状默认已是 0 ✅），
   则 `growth` 只依赖 `T`，而 `T` 的昼夜分量**在日尺度上均值化** ⇒ 退化成情形 A

**⚠️ 关键问题**：如果为了 R3 而"把昼夜分量解析化/均值化"，**世界就少了一个真实的周期驱动**
（原有的昼夜节律对觅食/信号机制有影响）。**这是纪元级改动，我们想先听你们的意见再定。**

### 6.3 定点化（你们 §5.4）

**接受，且我们认为是性价比最高的一条纪律改动**（它把"归约顺序"整类问题一次性消掉）。
